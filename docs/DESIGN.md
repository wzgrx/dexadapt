# DexAdapt 设计方案

> 状态：草案，待确认后实施。

## 0. 要解决的问题

LSPosed / Xposed 模块靠 Hook 宿主 App 的类和方法工作。宿主每次升级都会重新混淆：类名、方法名、字段名大量变化
（实测：小红书 9.49.1 → 9.50.0，模块用到的 512 个 Hook 点里 188 个换了名字）。传统做法是每个版本手工找一遍、
写死一张名字表，升级一次就要重新适配一次。

DexAdapt 是一套**通用**（不绑定任何 App、任何模块）的工具链加运行时库，做三件事：

1. **看懂升级**：两个版本的 APK 之间到底变了什么（包、清单、原生库、代码、接口、字符串），模块用到的点哪些会坏、为什么。
2. **写一次、跟着版本走**：Hook 点用“稳定特征”描述（查询），在任何版本上自动解析出当前的位置；模块装在新版本上也能当场适配。
3. **提前发现、自动修复**：量化每条查询有多脆弱，多版本矩阵回归；新版本解析失败时自动给出修复建议，甚至自动生成查询。

## 1. 核心思路

**不写名字，写特征。** 一个 Hook 点不是 `com.xingin.a.b#c`，而是“引用了字符串 `feedbackOverlay` 的类里、参数为
(String, int, 某 Bean, String, ViewGroup, String) 的那个方法”。特征按跨版本稳定程度分三档：

| 档 | 特征 | 例子 |
|---|---|---|
| 锚（最稳） | 字符串常量、没混淆的类名和成员名、Gson / 序列化字段名、注解（Retrofit 路径）、资源名 | 日志文字、埋点名、接口路径 `/api/sns/v1/...` |
| 关系 | 调用了谁、被谁调用、在哪里被 new、读写哪个字段、和谁同包、被谁当字段类型 | “被那个已知方法调用的唯一同形状方法” |
| 形状（最弱） | 参数、返回值、修饰符、父类、接口、字段类型 | `(String,int)V`、`static` |

**唯一命中才算找到**，多命中和零命中都算失败、不猜。查询之间可以互相引用（先找到类，再在类里找方法），形成依赖图。

**同一套查询，两个解析引擎，结果必须一致**：

- 电脑上：dexlib2 全量索引（完整的字符串表、调用图、字段引用），用来生成内置表、做分析和自动生成；
- 手机上：DexKit（原生、按需、省内存），模块在新版本上现场解析。

两者共用同一个解析器，只是“候选从哪里来”不同。这一点已经在红薯助手上验证：4 个小红书版本 × 512 个符号，
DexKit 与 dexlib2 结果逐条相同。

## 2. 总体架构

```
                    ┌─────────────────────────── 电脑（开发 / CI）────────────────────────────┐
  APK 样本仓库 ──▶  │ dexadapt-cli: inspect · diff · resolve · matrix · suggest · repair · export │ ──▶ 报告（MD/HTML/JSON）
  apks/<app>/<vc>   │        │ 用                                                                 │ ──▶ 内置符号表（随模块打包）
                    │   dexadapt-core（查询模型、解析器、表、指纹、余量、矩阵、spec 读写）      │
                    │   dexadapt-dexlib（全量索引）   dexadapt-dexkit（桌面 libdexkit）         │
                    └────────────────────────────────────────────────────────────────────────────┘
                    ┌─────────────────────────── 手机（模块运行时）───────────────────────────┐
                    │ dexadapt-android：本机适配（DexKit）、缓存与失效、发布给宿主进程、自检、诊断 │
                    │ 宿主进程里：按表取 Class/Method/Field，缺失的符号只停用依赖它的功能          │
                    └────────────────────────────────────────────────────────────────────────────┘
```

### 模块

| 模块 | 运行在 | 内容 |
|---|---|---|
| `dexadapt-core` | 纯 Kotlin/JVM（Android 可用） | 查询模型与 DSL、`SymbolResolver`、`SymbolSource` 接口、符号表格式、目录指纹、依赖图检查、余量分析、矩阵与漂移计算、spec（YAML/JSON）读写 |
| `dexadapt-dexlib` | 电脑 | dexlib2 全量索引数据源；APK 结构读取（给 diff 用） |
| `dexadapt-dexkit` | 手机 + 电脑 | DexKit 数据源（批量字符串预取、条件下推）；`scripts/build-dexkit-desktop.sh` 构建桌面版原生库 |
| `dexadapt-diff` | 电脑 | APK 升级分析（见第 3 节） |
| `dexadapt-synth` | 电脑 | 查询自动生成与修复（见第 5 节） |
| `dexadapt-cli` | 电脑 | 命令行，所有能力的入口；可进 CI |
| `dexadapt-android` | 手机 | 模块用的运行时库（见第 4 节） |

技术栈：Kotlin（JVM 17 字节码，兼容 Android）、Gradle 多模块、kotlinx-serialization、dexlib2、DexKit（版本统一在
`libs.versions.toml`）。发布到本地 Maven / GitHub Packages；红薯助手先用 Gradle 复合构建（`includeBuild`）直接引用源码。

### 查询（spec）的两种写法

同一个模型，两种入口：

- **Kotlin DSL**（模块代码里写，类型安全、能互相引用）：
  ```kotlin
  object FeedCopy : SymbolGroup("feedCopy") {
      val bean = cls("feedbackBean", ClassQuery(strings = listOf("CommonFeedBackBean(position=")))
      val overlay = cls("overlay", ClassQuery(strings = listOf("feedbackOverlay", "dsl/negative_feedback_mask_view")))
      val show = method("showOverlay", MethodQuery(owner = Of(overlay), shape = MethodShape(
          params = listOf(type("java.lang.String"), type("int"), Of(bean), type("java.lang.String"),
                          type("android.view.ViewGroup"), type("java.lang.String")), returns = type("void"))))
  }
  ```
- **YAML / JSON**（不写 Kotlin 也能用、工具好生成，沿用本仓库原来的 spec 习惯）：
  ```yaml
  app: com.xingin.xhs
  symbols:
    feedCopy.overlay:  { class: { strings: [feedbackOverlay, dsl/negative_feedback_mask_view] } }
    feedCopy.showOverlay:
      method:
        owner: $feedCopy.overlay
        params: [java.lang.String, int, $feedCopy.feedbackBean, java.lang.String, android.view.ViewGroup, java.lang.String]
        returns: void
  ```
  `$id` 引用其它符号。两种写法可以互相导出。

### 符号表（名字表）

解析结果：`符号 id → 当前版本的位置`（类名；方法的所属类、名字、参数、返回；字段的所属类、名字、类型），外加
`missing`（解析不到的及原因）、dex 摘要、spec 指纹、引擎版本、生成方式和时间。JSON，向后兼容（读到不认识的条目只把那一条记为缺失）。

## 3. 问题一：升级以后，分析出详细升级了什么（`dexadapt diff old.apk new.apk`）

输出一份报告（Markdown / HTML / JSON），从外到内：

| 层 | 内容 | 用处 |
|---|---|---|
| 包 | 版本名 / 号、minSdk / targetSdk、签名证书（是否同一个签名、是否被重签）、拆分包、ABI、大小 | 一眼看出是不是正规包（今天 Play 9.49.2 的镜像包就是被重签的） |
| 清单 | 权限增删；Activity / Service / Receiver / Provider 增删；exported、intent-filter、进程名变化；meta-data | 新功能入口、新的跳转页面 |
| 原生库 | `.so` 增删、大小变化、导出符号（`JNI_OnLoad`、`Java_*`）变化 | 新加的原生检测、加固 |
| 资源 | assets 和 res 文件增删；资源名增删（resources.arsc） | 布局 id、开关配置 |
| 代码概览 | 类 / 方法 / 字段数；按**未混淆**包（`com.xingin.xxx`）统计增删 | 哪个业务模块改得多 |
| 稳定 API | 没混淆的类：类、方法签名、字段的增删改 | 直接可读的接口变化 |
| 混淆映射 | 旧版混淆类 → 新版混淆类的对应关系（带置信度），未配上的列为“新增 / 删除” | 把“188 个名字变了”还原成“其实是同一个类改了名” |
| 字符串 | 字符串常量增删，单独列出接口路径、埋点名、日志 tag、配置 key、Retrofit 注解路径 | 新功能、新接口最直接的线索 |
| 模块视角 | 给了 spec 时：每个符号旧位置 → 新位置、哪些失效、失效在哪个条件（例如“参数 3 的类型变了”） | 升级后模块哪里会坏、为什么 |

**混淆映射怎么做**（核心算法）：

1. 每个类算一个结构指纹：字符串集合、方法形状的多重集（参数个数和基本类型、返回类型类别）、字段类型（只认稳定类型）、
   父类 / 接口（稳定的直接比，混淆的递归用映射）、调用了哪些稳定 API；
2. **锚定**：类名没混淆的、带独有字符串的，先一一配对；
3. **传播**：已配对类的调用者、被调用者、字段类型、父类，按指纹相似度在小范围里配对，迭代到不动点（BinDiff 式）；
4. 每对给置信度（几个特征吻合、有没有竞争者），歧义的不强行配；
5. 方法、字段在已配对的类里按形状和字符串再配。

这张映射还会被第 5 节的“修复”复用。

## 4. 问题二：不同版本、升级以后，模块自动适配（`dexadapt-android`）

三层兜底：

1. **内置表**：发版前用 CLI 对已知版本生成，随模块打包。宿主是这些版本时直接用，零等待。
2. **本机适配**：其它版本，在模块 App 进程里用 DexKit 解析宿主 APK（base + 带代码的拆分包），生成本机表：
   - 时机：首次打开、模块更新、宿主更新（`PACKAGE_REPLACED`）、定期；宿主进程发现没表时也可以通过桥请求；
   - 缓存键：宿主 APK 身份（路径、大小、更新时间、dex 摘要）+ spec 指纹 + 解析器 / DexKit 版本，任一变化就重扫；
   - 发布给宿主进程：libxposed 的远程文件（或模块自己的 provider），宿主进程读到后**热适配**（不用重启）；
   - 性能：一次批量字符串预取、条件下推给 DexKit、单线程、有进度；红薯助手实测 512 个符号手机上约 3 秒。
3. **降级**：解析不到的符号，只停用依赖它的功能（每个功能声明 `requires`），其余照常；原因报给模块界面。

运行时 API（宿主进程里）：

```kotlin
val symbols = DexAdapt.load(xposed, spec)           // 内置表 → 本机表 → 都没有就全部缺失
val show: Method = symbols.method(FeedCopy.show)    // 取不到抛异常，由功能框架记为“未适配”
val hide: Method? = symbols.methodOrNull(FeedCopy.hide)  // 可选符号
```

另外：

- **自检**：内置版本也可以让 DexKit 再解析一遍和内置表比对（发现同版本号的不同构建、被修改的包）。
- **诊断**：本机表和失败原因可以一键导出，开发者拿到就能用 `repair` 复现。
- **安全**：只读分析，不改宿主；表来自远端时（可选的在线更新）必须验签。

## 5. 问题三：怎么做一个非常强大的 DexKit 自动适配

“强大”= 解析得准 + 新版本上还能解析 + 坏了能很快修好。分五块：

### 5.1 表达力：查询能描述的特征

在现有基础上（字符串、类名、Gson 字段、父类 / 接口、字段类型、方法形状、调用、被调用、创建、字段读写、同包、字段持有、
排除兄弟、R8 把调用改到子类上的识别、桥接 / 合成方法的剔除）补充：

- 注解（Retrofit `@GET("/api/...")`、`@SerializedName`）、常量数字（特征明显的 magic number）；
- 资源：按资源名找 id（布局 id、字符串 id 每版会变，运行时 `getIdentifier`，也写进 spec 统一管理）；
- 字符串匹配方式：全等 / 包含 / 前缀 / 正则（DexKit 原生支持）；
- 方法体特征：调用次数、调用顺序（“先调 A 再调 B”）；
- 多版本条件：`absentIn`（某版本确实没有这个功能）、`pin`（极少数实在描述不了的，只对已知版本生效，本机适配时忽略）。

### 5.2 准：解析器规则

- 先用最强的锚选起点（字符串 > 类名 > 关系 > 包），再用其余全部条件过滤，唯一才算；
- 依赖图拓扑求解，成环、前向引用给出明确错误（不是空指针）；
- 钉死的位置也要符合查询的其它条件；
- 两个引擎同一解析器，矩阵里校验一致。

### 5.3 稳：脆弱度量化与门禁

- **余量**：逐个去掉查询里的一个条件，看是否还唯一。只靠一个条件撑着的叫“单点依赖”，只靠形状的最危险；
  类查询里的方法条件按子条件算（`methods[0].strings["x"]`、`methods[0].params` …），方法里有字符串这类锚撑着就不算只靠形状；
- **版本矩阵**：同一 spec 在 N 个历史版本上跑，统计每个符号的解析情况和漂移（位置变化）；
- **CI 门禁**：新加的查询必须在全部样本版本上唯一命中，且不能是“仅靠形状的单点依赖”；
- 健康分：每个符号一个分数（锚的数量和强度、余量、历史版本通过率），功能级汇总。

### 5.4 自动生成查询（`dexadapt suggest`）

开发者在某个版本里找到了目标（例如 jadx 里看到的 `sa9.g0#h(ViewGroup)`），工具自动写查询：

1. 收集目标的全部特征（字符串、调用、被调用、字段、形状、所在类的特征、同包锚点）；
2. 按稳定度给特征打分，贪心挑出能让它**唯一**的最少、最稳的组合（优先锚，其次关系，最后形状）；
3. **跨版本验证**：在样本仓库的其它版本上解析，要求都唯一命中且指向“同一个东西”（用第 3 节的映射判断）；
4. 输出 Kotlin DSL / YAML 和它的余量，开发者确认后写进 spec。

### 5.5 自动修复（`dexadapt repair`）

新版本里某些符号解析失败时：

1. **诊断**：逐个条件检查，指出是哪个条件不满足（字符串没了？参数类型变了？多出一个同形状兄弟？）；
2. **推断**：用旧版本的位置 + 第 3 节的混淆映射，找到新版本里对应的成员；
3. **重写**：以新位置为目标走一遍 5.4，生成新查询，并在新旧版本上都验证；
4. 输出补丁（spec 的 diff）和报告。

可选的运行时自愈：手机上解析失败时按同样思路给出“推测位置”，但只在通过形状校验、并标记为推测的情况下由模块自行决定是否启用，默认关。

## 6. 问题四：其它值得做的

- **APK 样本仓库**：`apks/<app>/<渠道>-<versionCode>/`，每个版本记来源、签名、dex 摘要（`PROVENANCE`）；diff 自动提示重签和被改过的包。
- **一条龙流程**：新版本 APK 放进仓库 → `diff` 出升级报告 → `matrix` 出健康度 → 失败的走 `repair` → 更新内置表 → 发版。可以挂到 CI。
- **功能视角**：符号 → 功能的映射，报告直接说“哪几个功能会坏”，而不是“哪几个符号缺了”。
- **名字表导出**：导出成扁平的名字表（id → 位置，普通 JSON），按名字表工作的老模块不改代码也能受益。
- **加固和动态加载**：壳把 dex 藏起来时，DexKit 读 APK 看不到真代码；提供运行时从宿主 ClassLoader 导出 dex 再解析的方案。
- **多进程、多 dex、拆分包**：按类加载顺序合并多个数据源（已在红薯助手实现）。
- **性能预算**：手机上限时、限内存，超时的查询记下来，矩阵里标出“慢查询”。
- **回归快照**：每个符号保存期望签名快照，CI 比对，防止查询改了以后“唯一但命中错了”。

## 9. 风险与边界

- 混淆映射是启发式，有误配可能：报告里只给置信度，不自动当真；`repair` 生成的查询必须过跨版本验证。
- 宿主大改（功能重写）时没有“对应”可言，工具只能告诉你“这块没了”，需要人看。
- 加固包需要运行时导出 dex，放在后面做。
- DexKit 原生库的桌面版要自己编译（脚本已有）；版本必须和手机上用的一致。

## 10. 进一步加强（候选，按价值排序）

### 10.1 找得到 ≠ 用得对：语义校验（P1）

解析出唯一的位置，不代表它还是原来那个意思（参数顺序变了、方法被拆成两个、返回值含义变了）。

- **Hook 契约**：spec 里给符号写“契约”——参数的期望（非空、取值范围、某个参数是 `View`）、调用频率、调用线程。
  手机上新版本第一次用时进入**观察模式**：只记录、不改行为，满足契约后才放开；不满足就当“未适配”。
- **方法体差异**：`diff` 对模块 Hook 的每个方法做字节码级比较（指令序列相似度、调用列表变化），升级报告里直接说
  “位置找到了，但方法体变了 40%，请复核”。
- **回归快照**：每个符号保存“期望签名 + 方法体指纹”，CI 比对，查询改了以后“唯一但命中错了”能被发现。

### 10.2 更多、更稳的锚：自动挖掘（P1）

很多 App 混淆后仍然留着能还原名字的信息，`suggest` 应该自动挖出来、优先用：

- 数据类的 `toString()` 字符串（`CommonFeedBackBean(position=`，红薯助手已经大量在用）；
- `SourceFile` 属性（不少 App 保留了源文件名做崩溃堆栈）、Kotlin `@Metadata` 里的原始名字、枚举常量名、
  `@SerializedName` / Retrofit 注解、`Log` tag、异常消息、埋点事件名、ARouter / 路由表里的页面路径。
- 对加密字符串的 App：识别解密函数，静态模拟或运行时取明文后再当锚用。

### 10.3 认出 App 里打包的开源库（P1）

App 里的 OkHttp、Retrofit、Gson、Glide、ExoPlayer、Fresco、RxJava 也被混淆了，但它们是**公开的**：

- 维护一个“开源库指纹库”（各版本官方 jar 的结构指纹），把 App 里的混淆类配回原名（类似 LibScout 的思路）；
- 好处：网络层、图片加载、播放器这类常用 Hook 点变成**跨 App 通用**的 spec（“Hook 任何 App 的 OkHttp 请求”），
  一次写好，所有模块都能用；`diff` 也能报告“OkHttp 从 4.9 升到 4.12”。

### 10.4 Hook 真能生效吗：内联与 ART 风险（P1）

LSPosed 的实际坑：Hook 的方法太小、只有一个调用者时，ART 可能把它内联，Hook 不触发。

- `matrix` / `suggest` 标出“可能被内联”的目标（方法体极短、final / private、单一调用者），建议改 Hook 调用者，
  或让运行时库对调用者做反优化（deoptimize）。
- 同理标出：抽象方法、接口方法（要 Hook 实现类）、`synchronized` / native 方法、动态代理（Retrofit 接口）。

### 10.5 类型安全的访问层：代码生成（P2）

模块里大量“按名字反射读字段”（`Reflect.get(feed, "poi")`），名字一变就静默拿到 null（今天修的地点问题就是这类）。

- 从 spec 生成 Kotlin 访问器：`NoteFeed.poi(feed)`、`FeedOverlay.hide(controller, parent)`，内部缓存 `Field` / `Method`，
  取不到时明确报“未适配”；字段也纳入 spec 和矩阵，名字变了在 CI 里就能发现。

### 10.6 共享适配表（P2）

- 同一个宿主版本，所有装了模块的手机解析结果都一样。可以由开发者（CI）对新版本生成表、签名后发布到 GitHub Releases，
  模块按 dex 摘要下载，比手机上自己扫更快、也经过了 CI 的全部校验；下载不到再本机适配。
- 只传版本号和摘要，不传用户数据；表必须验签。

### 10.7 新版本跟踪与一条龙自动化（P2）

- 手机上的模块发现宿主升级时，在诊断里记下新版本号和摘要，提醒开发者“有用户已经在用 9.51.0”；
- 开发者把 APK 放进样本仓库后，CI 自动：`diff` 出升级报告 → `matrix` 出健康度 → 失败的跑 `repair` → 开 PR 更新 spec 和内置表；
- 报告以 HTML 发布（矩阵热力图：符号 × 版本，颜色表示通过 / 漂移 / 失败），PR 里附摘要。

### 10.8 运行时更强（P2）

- **按需解析**：先只解析当前要用的功能的符号，后台再补全，冷启动更快；
- **分级回退**：查询失败时，先试“去掉最弱条件后是否唯一”（用余量数据），再试上次版本位置 + 映射推断；结果标为“推测”，
  只在观察模式验证通过后启用；
- **远程开关**：已知某版本某功能会坏，可以下发“停用这个功能”的签名配置，不用等发版。

### 10.9 开发体验（P3）

- spec 检查器（lint）：前向引用、只靠形状、正则过宽、引用了不存在的符号、和别的符号命中同一个成员；
- jadx 插件 / 命令：在 jadx 里选中一个方法 → 直接生成查询（调 `suggest`）；
- 桌面索引缓存：每个 APK 只建一次索引，矩阵并行跑；
- 模拟器自动化：有 root 和 LSPosed 的模拟器镜像里装多个宿主版本，自动跑冒烟场景、收日志（真机只做最后确认）。

### 10.10 分析范围扩展（P3）

- 加固 / 动态加载：运行时从宿主 ClassLoader 导出 dex，再交给同一套解析；
- 原生层：`.so` 导出符号和字符串的差异，给需要 Hook 原生函数的模块用。

### 11.2 据此新增的设计点

1. **指纹生态兼容**：导入 ReVanced / Morphe 指纹、QAuxiliary 的 `DexKitTarget` 写法，转换成 DexAdapt 查询；也能反向导出。
2. **指令过滤器**：方法体里“按顺序出现”的调用、字面量、字段读写、操作码类别，作为一类新特征（比整段操作码序列稳得多）。
3. **混淆映射按四阶段流水线实现**，并且：
   - 输出 ProGuard `mapping.txt`，jadx / retrace 直接用；
   - 用红薯助手 512 个符号 × 4 个版本做**标注集**，报告精度和召回（像 twinflame 的基准一样持续跟踪）。
4. **APK 指纹记录文件**：每个 APK 只建一次索引，存成紧凑的记录文件（类似 twinflame 的 `.tfr`），矩阵和 diff 直接读记录，快很多。
5. **MCP 服务**：`dexadapt mcp` 暴露 inspect / diff / resolve / suggest / repair，配合本机已有的 jadx MCP，让 Agent 完成“新版本来了 → 出报告 → 修查询 → 开 PR”。
6. **运行时缓存层接 `DexKitCacheBridge`**：表级缓存（我们的）放在它之上，bridge 复用和空闲释放交给 DexKit；实验性 API 包在适配层里。
7. **R8 感知**：识别 `$$ExternalSyntheticLambda`、`$r8$` 外提方法、合并后的类；diff 里把“R8 优化造成的结构变化”单独归类，不算功能改动。
8. **Hook 框架适配**：给 YukiHookAPI、EzXHelper、KavaRef 以及原生 libxposed 提供“表 → Method / Field”的小适配层，模块不用改 Hook 写法。

## 12. 双模块运行时一致性（0.4.0）

- 契约判定采用独立规则指纹及目标身份；规则调整只触发重新观察，不触发不必要的DEX重扫。拒绝NaN与无穷输入。
- MCP把协议读取与单个重任务分开，支持取消、明确的退出状态、结构化结果及有界输出。
- base与代码split使用同一内容摘要算法；包名/构建/完整代码集合区分缓存，资源split不改变单代码包摘要。
- 安装期间记录实际读取的符号，换表按目标变化而非仅缺失恢复重绑；启动阶段功能保留重开提示，失败恢复原表。
- 两个使用方共用身份与绑定差异策略；UI与业务校验保留在各自模块，验证含已知APK、同码异渠道与合成拆包。

## 13. 多签名与只读探查（0.5.0）

同一个方法符号可以保留原形状和多个备用形状。每个形状单独匹配，共用所属类、包、调用和字段关系；已知构建
优先使用明确指定给它的形状（DEX 摘要优先于构建标识），没有相应选择器时把所有形状的结果按完整签名合并。
不同方法同时匹配仍是歧义。存在无法核对的依赖时不允许靠其它形状掩盖错误；已知构建未选中的形状不参与解析。
构建标识仅由已识别的调用方提供；直接传入 CLI 时由使用者负责识别。DEX 选择器核对实际打开的代码摘要。

`probe` 只跑解析，不生成适配表、不做余量扫描。可同时读旧 spec，在同一个包上列出定位改变、退化和恢复的符号；
对旧客户端重复执行即可验证影响范围。缺失条目区分直接失败和依赖失败，多签名失败附各形状的命中数及少量候选。

## 14. 多签名访问器与按符号复用余量（0.6.0）

单签名的 Kotlin 访问器保持原接口。多签名访问器只承诺各形状共同的返回类型，接收当前宿主的参数列表；由
SymbolLinker 用同一次查表拿到实际成员，验证接收者、参数个数和类型后再调用。构造方法不收接收者。
不试调其它分支，不丢弃或补写参数；业务层自行决定不同版本中新增参数的语义。

桌面矩阵先确认包名、构建和实际 DEX 摘要，再判断是否需要打开索引。完整命中可直接复用；
目录变化时重新解析表，仅对查询或依赖变化的符号重算余量。每条余量指纹覆盖自己的查询、钉子和缺省声明，
以及所有递归依赖；余量仍用完整候选集计算。保守地使整个依赖链失效，包括备用签名所引用的类型。
有缺失或计算异常的结果不能当成可复用的成功记录。发布验收用独立全量结果核对增量，并始终重新跑 DexKit 对照。

本节的增量只针对桌面余量，不改变手机上的匹配规则。缓存按实际内容校验；任何缓存缺失都能回到全量计算。
`manifest.json` 的余量数量按被检查的符号计数，包括无需计算余量的固定位置或明确缺省项。

## 15. 拆包内容身份与按符号解析（0.7.0）

拆包缓存按有序成员名和实际 APK 字节 SHA-256 定位，与外层文件名和大小无关。读缓存时重新校验每个成员；
缺失或损坏的成员先写临时文件、校验后原子替换。提取失败不把不完整文件当作缓存命中。

桌面矩阵在完整 DEX、引擎、包和构建身份一致时，按自身查询及递归依赖指纹复用成功解析的成员。缺省声明仍按
当前构建重新计算，失败不复用。变化的符号及其下游重新查找，查找时允许引用已核验的缓存依赖。余量和解析结果
分别记录；余量无法计算不影响有效位置的复用。完整发布对照仍独立计算 Dexlib 与 DexKit。

## 16. 宿主升级后的恢复流程（0.8.0）

宿主启动、安装变动、模块启动和周期检查共用一个运行时协调器。Android 端负责投递这些事件、取得已安装宿主的
包名、版本号与完整 DEX 摘要，并用持久任务在进程重启后重投。协调器每进程只允许一个扫描执行；同一任务去重，
连续更新取消旧任务的发布资格。各阶段与最终表发布前均重查安装身份；消费方按身份再次验证。降级可以复用与
当前完整 DEX 及查询目录完全匹配的已完成表。

先解析已启用功能及依赖，阶段表只给允许热安装的功能使用，不作为完整表保存。剩余目录随后解析；需要在宿主
启动时安装的功能等完整表并提示重启。扫描中断后可重投，只有完整表能进入持久缓存。首个功能恢复耗时以消费方
确认安装成功为准，解析到符号不等于功能生效。旧选表接口保留供已发布使用方兼容，新流程使用严格接口。

## 17. 恢复确认与分段计时（0.9.0）

表已经发送、框架登记成功、功能实际干预是不同事件。以请求编号、完整 DEX 身份和目录指纹关联宿主确认，
只有同一发布代际的确认才能推进状态；失败保留为可重试状态，过期发布和确认丢弃。
回执在一次同步操作内验证发布令牌、当前安装身份和目录，区分首次推进、幂等重放与拒绝；使用方只对首次失败安排重试。
持久适配表不带进程内令牌。完整表内容可以跨进程复用，但交付时必须重新发行令牌。

身份验证在一次安装快照内复用已经读取的完整 DEX 字节摘要。快照同时核对文件标识、大小、修改时间及文件状态变化时间；
系统无法提供可靠的变化标记，或秒级变化时间尚处于同一写入窗口时，重新读 DEX。各包独立读取，安装变更可以立即使进行中的摘要失效。缓存仅限进程内。


## 18. 共用恢复状态机与统一时序（0.10.0）

模块端按完整身份维护当前交付和有界失败预算。宿主端暂存绑定与首次效果，用退避自动补报；
收到旧令牌拒绝时，只对同一个已验证表重新申请令牌。补发在身份、目录和表内容都一致时不重新扫描。
宿主观察到的时间与模块接收时间分别记录；工作排队、解析阶段和确认事件通过交付令牌串联。

## 19. 前台恢复快路径（0.11.0）

已鉴权的宿主请求先核对完整安装身份和查询目录。完整表命中时经同一次桥接调用交付；缺表时才进入持久队列。
安装身份暂不可读、宿主已换版或当前交付已被拒绝时不返回旧表。阶段表、完整表和宿主观察分别计时。
首个效果的观察时间与回执到达时间分别记录；续发后的早期观察不再被压成零。摘要缓存记录实际完整读取次数，
用于区分手机端摘要缓存命中和文件系统缓存命中。

### 0.12：桥接就绪与安装代际

恢复回执与符号链接缓存分离：只改令牌时复用已经校验的反射对象及读取快照，不重装 Hook。
桥接首次确认可用时通知恢复待发箱，撤销尚未执行的退避；同一轮只保留一个在途续发/补报，
保留原绑定、首效观察时间。超时和 Binder 断开仍有有界退避，不重放业务写请求。

完整 DEX 摘要可保存在使用方自己的私有目录。缓存键包含包名、版本、安装更新时间，以及按加载顺序排列的
所有代码/资源 APK 的路径、大小、inode、mtime 与 ctime（完整精度）。每次命中前后重取安装快照；
缺少可靠文件身份、最近秒级 ctime、内容/安装代际变动或损坏记录时重新读完整 DEX。
缓存只保存已经完整计算的 SHA-256；元数据不代替首次内容校验，不相信宿主传入的摘要。
宿主与模块各用自己的私有缓存，不开放共享写入。进程内并发合并；跨进程通过文件锁串行冷读取。

### 0.13：跨进程核验票据、阶段通知与分段计时

模块先计算完整 DEX SHA-256，按包名、版本、系统安装更新时间和全部有序 APK 的可靠文件身份发布票据。
票据只经模块控制的 LSPosed 远程文件提供；文件名绑定当前快照，宿主核对读取前后快照后才能导入自己的私有缓存。
通道不可用、内容损坏或身份无法可靠比较时继续完整读取。已知票据不能替代未知安装的首次内容校验，
不接受宿主回传或公共可写目录提供的摘要。两侧分别记录实际完整摘要计算次数，计时包含准备阶段。

宿主经已经鉴权的 Provider 注册 Binder 通知端点，模块发布部分/完整表后只推送就绪标记。
通知核对模块 UID、宿主完整身份、目录、服务代际和递增序号；不传信任豁免或直接替换表。
宿主醒来重新读取并核对表；Binder 断开重注册，保留轮询兼容回退。进度与通知合并，不在扫描线程阻塞回调。

计时覆盖安装快照、锁等待、票据/私有缓存、ZIP读取与解压、SHA更新、DexKit初始化、阶段预取、
逐符号解析（含缓存命中）、表交付、宿主绑定及原始首效。结果写验证材料，不进入产品设置流程。

显式全量扫描走同一协调器但跳过已有表复用，自检仍保留逐项比较。已有完整表的宿主订阅后可接收
运行中新完整结果；目标完全相同时只更新交付元数据并保留反射缓存。模块进程的 Binder 端点死亡后，
宿主在后台有限重订阅，通知 UID 和服务代际仍重新验证，不靠重新触发功能恢复订阅。

缓存依赖命中按阶段汇总次数，不逐次分配计时样本；关闭计时保持原解析快路径。读取租约使用独立的跨进程单调时钟，不能受计时采集开关影响。
